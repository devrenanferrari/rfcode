# Como criar sites, apps e sistemas (front-end e frameworks)
- Comece pela escolha da stack pelo tipo de projeto, não pela moda: site de conteúdo/marketing ou blog -> Astro ou um SSG (Starlight/Docusaurus para docs); app com muita interação (SPA) -> Vite + React/Vue/Svelte/Solid; app que precisa de SSR, rotas de servidor, SEO e dados -> meta-framework (Next, Nuxt, SvelteKit, SolidStart, Astro); API/serviço -> Nest, Hono ou Express; desktop -> Tauri (leve) ou Electron; mobile -> Expo. Na dúvida entre dois, prefira o que o projeto/time já usa.
- Não reinvente a base: use web_scaffold para o esqueleto oficial e só então programe em cima. Se o usuário não disse a stack, pergunte uma vez (ou escolha a mais simples que atende e diga o porquê). Depois do scaffold, rode o projeto (npm run dev) ou use serve para pré-visualizar, e confira que sobe antes de continuar.
- Estrutura: componentes pequenos e com responsabilidade única; separe UI de lógica/estado; co-localize arquivos por funcionalidade (feature folders) em projetos maiores. Siga a convenção do framework (pasta de rotas, app/ vs pages/, layouts) em vez de inventar.
- Estado: comece com o estado local e o do próprio framework; só adicione uma lib de estado global (Zustand, Pinia, stores do Svelte, TanStack Query para dados de servidor) quando a dor aparecer. Dados de servidor != estado de UI.
- Estilo: prefira o que a stack já traz ou Tailwind (web_scaffold adiciona). Para componentes prontos e acessíveis, shadcn/ui (React) economiza tempo. Mantenha tokens de design (cores, espaçamento) em um lugar só.
- Qualidade inegociável: acessibilidade (HTML semântico, foco, labels, contraste, teclado), responsivo (mobile primeiro), e desempenho (imagens otimizadas, code splitting, medir antes de otimizar). Rode o linter/formatador do projeto (code_quality) e os testes antes de concluir.
- Verifique de verdade: build sem erros, a página abre e a funcionalidade principal funciona (sirva e abra, ou rode os testes/e2e). Não diga "pronto" sem ter visto rodar.
- Aprenda o projeto: ao descobrir como rodar/buildar/testar e as convenções, guarde com learn; se repetir um fluxo (criar página, componente, rota), cristalize num comando com crystallize.
- Frameworks mudam rápido: se um comando de criação ou uma API parecer diferente do que você lembra, confirme com deep_research/web antes de afirmar. Não invente flags.
